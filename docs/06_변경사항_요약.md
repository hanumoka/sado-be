## 2. 모듈 구조 변경 (5개 → 6개)

### 변경 전
```
sado-be/
├── common/              # 공통 모듈
├── minipacs/            # DICOM 관리
├── auth/                # 인증/인가
├── gateway/             # API Gateway
└── bff/                 # Backend For Frontend (모든 비즈니스 로직 포함)
```

### 변경 후 ✅
```
sado-be/
├── sado-common/         # 공통 모듈 (core, event, security 분리)
├── sado-infrastructure/ # ⭐ 인프라 모듈 추가
├── sado-gateway/        # API Gateway (Keycloak 직접 연동)
├── sado-minipacs/       # DICOM 관리 (api, domain, storage 분리)
├── sado-orchestrator/   # ⭐ 워크플로우 오케스트레이션 (BFF에서 분리)
└── sado-bff/            # 프론트엔드 API 조합만 담당
```

**주요 변경점**:
1. **Auth 모듈 제거**: Gateway에서 Keycloak 직접 연동
2. **Infrastructure 모듈 추가**: Kafka, Redis, Temporal, Storage 설정 통합
3. **Orchestrator 모듈 추가**: BFF에서 비즈니스 워크플로우 분리
4. **BFF 모듈 재정의**: 본래 의미인 "프론트엔드 API 조합"만 담당

## 3. BFF vs Orchestrator 역할 분리

### 변경 전: BFF가 과도한 책임
```
BFF 역할:
- 이벤트 컨슈밍 (MiniPACS 이벤트)
- Triton 서버 AI 분석 요청
- 분석 결과 저장
- 리포트 생성
- 프론트엔드 API 제공
```

### 변경 후: Orchestrator + BFF ✅

#### Orchestrator (신규)
```
역할:
- 이벤트 컨슈밍 (MiniPACS 업로드 완료)
- Triton 서버 AI 분석 요청 (REST API)
- Temporal Saga 패턴 구현
- 분석 결과 저장 및 이벤트 발행
- 장기 실행 워크플로우 관리

기술:
- Temporal Workflow & Activity
- Kafka Consumer
- REST Client (Triton 연동)
```

#### BFF (재정의)
```
역할:
- 프론트엔드 API 조합 (MiniPACS + Orchestrator 결과)
- UI 친화적 데이터 포맷 반환
- GraphQL API 제공 (선택, Phase 4)

기술:
- REST Controller
- GraphQL (선택)
```

**변경 이유**: BFF가 "Backend For Frontend"의 본래 의미를 벗어나 비즈니스 로직까지 담당하고 있었음. 워크플로우 오케스트레이션은 별도 모듈로 분리하는 것이 MSA 학습에 적합.

## 4. 이벤트 플로우 변경

### 변경 전: Triton 서버가 Kafka Consumer 구현
```
MiniPACS → Kafka Event A → Orchestrator → Kafka Event B → Triton Server
                                                              ↓
                                      Kafka Event C ← Triton Server
                                              ↓
                                        Orchestrator
```

### 변경 후: Triton 서버는 REST API ✅
```
MiniPACS → Kafka Event A → Orchestrator → REST POST → Triton Server
                                                            ↓
                                              REST Response (Callback)
                                                            ↓
                                                      Orchestrator
                                                            ↓
                                                    Kafka Event (분석 완료)
                                                            ↓
                                                          BFF
```

**변경 이유**:
- AI 서버(Triton)가 Kafka Consumer를 구현하는 것은 기술 스택 결합도가 높음
- REST API 기반이 AI 팀과 백엔드 팀 간 느슨한 결합 유지
- 학습 목적으로도 REST API 연동 패턴이 더 실용적

```

- PostgreSQL / MySQL - 선택 필요

```

```
- RabbitMQ (학습 목표와 부합하지 않음)

- Debezium (Phase 1-3에서 불필요, Outbox Pattern 우선)
```

## 6. 단계별 구현 계획 변경

### 변경 전: 5단계 (11-16주)
```
Phase 1: 기반 구축 (2-3주)
Phase 2: 핵심 기능 (3-4주)
Phase 3: 워크플로우 (2-3주)
Phase 4: 고급 기능 (2-3주)
Phase 5: 최적화 및 배포 (2주)
```

### 변경 후: 4단계 (16주) ✅
```
Phase 1 (POC, Week 1-4):
  - 멀티모듈 구조
  - PostgreSQL + JPA
  - Gateway 기본 라우팅
  - 첫 E2E 플로우 완성

Phase 2 (Kafka 마스터, Week 5-7):
  - Kafka 아키텍처 심화
  - Schema Registry & Avro
  - Outbox Pattern
  - 3주 동안 Kafka만 집중 학습

Phase 3 (Temporal 마스터, Week 8-10):
  - Temporal Workflow & Activity
  - Saga 패턴 완전 이해
  - 보상 트랜잭션 구현
  - 3주 동안 Temporal만 집중 학습

Phase 4 (완성, Week 11-16):
  - SeaweedFS & Keycloak (Week 11-13)
  - Redis, Monitoring, 포트폴리오 (Week 14-16)
```

**변경 이유**:
- 각 기술마다 2-3주씩 집중 학습 시간 확보
- "사용" 수준이 아닌 "마스터" 수준 목표
- 학습 내용 문서화 시간 포함
