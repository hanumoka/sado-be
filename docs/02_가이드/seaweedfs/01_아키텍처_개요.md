## SeaweedFS란 무엇인가

### 정의

**SeaweedFS**는 **수십억 개의 작은 파일을 효율적으로 저장**하기 위해 설계된 빠른 분산 스토리지 시스템입니다.

```
"SeaweedFS is a fast distributed storage system for blobs, objects, files,
and data lake, for billions of files!"
```

### 핵심 특징

| 특징 | 설명 |
|-----|------|
| **O(1) 디스크 읽기** | 단 한 번의 디스크 seek으로 파일 읽기 |
| **수십억 개 파일** | 메타데이터 오버헤드 단 40 bytes |
| **S3 호환** | AWS S3 API와 호환되는 인터페이스 |
| **POSIX 지원** | Filer를 통한 파일 시스템 인터페이스 |
| **자동 복제** | 데이터센터/랙 인식 복제 |
| **경량** | 단일 Go 바이너리 (weed) |
| **Cloud Tiering** | HOT/WARM/COLD 스토리지 티어링 |
| **Erasure Coding** | 스토리지 비용 절감 |

### 주요 사용 사례

✅ **콘텐츠 전송 네트워크 (CDN)**: 이미지, 비디오 썸네일
✅ **의료 영상 저장 (PACS)**: DICOM 파일 (SADO 프로젝트!)
✅ **소셜 미디어**: 사용자 업로드 사진
✅ **로그 저장소**: 시계열 로그 파일
✅ **백업 시스템**: 대용량 백업 데이터

## 설계 배경: Facebook Haystack

### Facebook의 사진 저장 문제

Facebook은 2009년 **수백억 장의 사진**을 저장하면서 전통적인 파일 시스템의 한계에 직면했습니다:

**문제점**:
1. **메타데이터 오버헤드**: 각 파일마다 inode, directory entry 등의 메타데이터 필요
2. **디스크 Seek 횟수**: 작은 파일 하나 읽을 때마다 여러 번의 디스크 seek 발생
   - Directory inode 읽기
   - Directory block 읽기
   - File inode 읽기
   - File data block 읽기
3. **캐시 비효율**: 메타데이터가 너무 많아 메모리에 캐싱 불가능

### Haystack 솔루션

Facebook은 **Haystack** 논문에서 혁신적인 아이디어를 제시했습니다:

```
핵심 아이디어: "파일을 개별적으로 저장하지 말고,
              큰 파일(Volume) 안에 바늘(Needle)처럼 쌓아라"
```

**Haystack의 접근 방법**:
- **Volume**: 큰 물리적 파일 (예: 32GB)
- **Needle**: Volume 안에 저장되는 실제 파일 데이터
- **In-Memory Index**: Volume의 모든 Needle 위치를 메모리에 캐싱

**결과**:
- ❌ 디스크 Seek 4번 → ✅ **1번**
- ❌ 메타데이터 캐싱 불가 → ✅ **전체 인덱스 메모리 캐싱**
- ❌ 느린 파일 읽기 → ✅ **10배 이상 빠른 읽기**

### SeaweedFS의 탄생

SeaweedFS는 Haystack 논문의 아이디어를 **오픈소스**로 구현한 것입니다:

```go
// SeaweedFS의 핵심 개념
Volume = {
    Physical File (32GB),
    In-Memory Index (Needle ID → Offset)
}

File Read = {
    1. 메모리에서 Offset 조회 (O(1))
    2. Volume 파일에서 Offset 위치 직접 읽기 (1 disk seek)
}
```

**참고 자료**:
- [Facebook Haystack Paper (2010)](https://www.usenix.org/legacy/event/osdi10/tech/full_papers/Beaver.pdf)
- [SeaweedFS Architecture PDF](https://raw.githubusercontent.com/wiki/seaweedfs/seaweedfs/SeaweedFS_Architecture.pdf)

## 핵심 아키텍처

### 전체 구조

SeaweedFS는 **3개의 주요 컴포넌트**로 구성됩니다:

```
┌─────────────────────────────────────────────────────────┐
│                    Client Application                    │
│                  (Spring Boot SADO)                      │
└──────────────┬──────────────────────┬───────────────────┘
               │                      │
               ↓ (1) Assign FID       ↓ (2) Upload File
        ┌──────────────┐       ┌──────────────────┐
        │    Master    │       │  Volume Server   │
        │    Server    │←──────│   (Storage)      │
        │  (Metadata)  │       │                  │
        └──────────────┘       └──────────────────┘
               ↑                        ↑
               │ Heartbeat              │
               │                        │
        ┌──────────────┐                │
        │    Filer     │                │
        │    Server    │────────────────┘
        │ (Filesystem) │    (Read/Write)
        └──────────────┘
```

### 컴포넌트별 역할

#### 1. Master Server (마스터 서버)
- **역할**: 클러스터 전체 조정자
- **책임**:
  - Volume 위치 정보 관리
  - 파일 ID (FID) 할당
  - Volume Server 상태 모니터링 (Heartbeat)
  - 복제 정책 관리
- **저장하지 않는 것**: 파일 데이터, 파일 메타데이터
- **포트**: 9333 (HTTP), 19333 (gRPC)

#### 2. Volume Server (볼륨 서버)
- **역할**: 실제 파일 데이터 저장
- **책임**:
  - Volume 내부에 파일 저장 (Needle)
  - 파일 읽기/쓰기/삭제
  - Master에게 Heartbeat 전송
  - Volume 인덱스 메모리 캐싱
- **포트**: 8080 (HTTP)

#### 3. Filer Server (파일러 서버)
- **역할**: 파일 시스템 인터페이스 제공
- **책임**:
  - 디렉토리 구조 관리 (`/photos/2025/12/image.jpg`)
  - 파일 메타데이터 저장 (이름, 크기, 권한 등)
  - Volume Server로 데이터 위임
  - S3 API 제공
- **포트**: 8888 (HTTP), 18888 (gRPC)
- **메타데이터 저장소**: MySQL, PostgreSQL, Redis, LevelDB 등

### 아키텍처 계층

```
┌─────────────────────────────────────────┐
│   Application Layer (Filer + S3 API)   │  ← POSIX, S3 호환
├─────────────────────────────────────────┤
│   Object Store (Master + Volume)       │  ← 핵심 계층
└─────────────────────────────────────────┘
```

**2-Layer 설계**:
- **Object Store**: Master + Volume (필수, 분산 객체 저장소)
- **Application Layer**: Filer + S3 (선택, 파일 시스템 인터페이스)

## O(1) 디스크 읽기 원리

### 전통적인 파일 시스템의 문제

**파일 하나를 읽을 때 필요한 디스크 Seek 횟수**:

```
1. Directory Inode 읽기      (Seek #1)
2. Directory Data Block 읽기 (Seek #2)
3. File Inode 읽기           (Seek #3)
4. File Data Block 읽기      (Seek #4)
```

**결과**: 작은 파일 하나 읽는데 **4번의 디스크 Seek** 💥

### SeaweedFS의 혁신적 방법

**Volume 구조**:

```
┌────────────────────────────────────────────┐
│           Volume File (32GB)               │
├────────────────────────────────────────────┤
│ Needle 1: [Cookie|Key|Size|Data|Checksum] │
│ Needle 2: [Cookie|Key|Size|Data|Checksum] │
│ Needle 3: [Cookie|Key|Size|Data|Checksum] │
│ ...                                        │
│ Needle N: [Cookie|Key|Size|Data|Checksum] │
└────────────────────────────────────────────┘
```

**In-Memory Index**:

```go
Volume Index (메모리):
  Needle ID → Offset

  12345678 → 0x00001000
  23456789 → 0x00FF2000
  34567890 → 0x01A3C000
```

**파일 읽기 프로세스**:

```
1. 메모리에서 Needle ID로 Offset 조회  (메모리 조회, O(1))
2. Volume 파일의 Offset 위치로 Seek   (Disk Seek #1)
3. 데이터 읽기                         (Disk Read)
```

**결과**: 작은 파일 하나 읽는데 **1번의 디스크 Seek** ✨

### 메타데이터 오버헤드

**전통적인 파일 시스템**:
- **inode**: ~256 bytes
- **directory entry**: ~32 bytes
- **total**: ~288 bytes per file

**SeaweedFS**:
- **In-Memory Index**: 16 bytes (Needle ID + Offset)
- **Disk Overhead**: 40 bytes (Cookie, Size, Checksum 등)
- **total**: ~40 bytes per file

**결과**: 메타데이터 오버헤드 **87% 감소** 🚀

## 왜 DICOM 저장에 적합한가

### DICOM 파일 특성

DICOM 의료 영상 파일은 SeaweedFS의 강점과 완벽하게 일치합니다:

| DICOM 특성 | SeaweedFS 장점 |
|-----------|---------------|
| **작은 파일 다수** | O(1) 디스크 읽기로 빠른 접근 |
| **Write-Once-Read-Many** | Append-Only Volume 구조에 최적 |
| **고유 식별자** | SOP Instance UID → FID 매핑 |
| **멀티프레임 영상** | 대용량 파일도 효율적 처리 |
| **썸네일/트랜스코딩** | 파생 파일도 함께 저장 |
| **장기 보관** | Erasure Coding으로 비용 절감 |

### SADO MiniPACS 시나리오

```
DICOM File Upload Flow:

1. Spring Boot receives DICOM file
   ↓
2. Parse DICOM metadata (dcm4che)
   ↓
3. Request FID from Master
   GET http://localhost:10400/dir/assign
   → Response: { "fid": "3,01637037d6" }
   ↓
4. Upload file to Volume Server
   POST http://localhost:10402/3,01637037d6
   ↓
5. Save metadata to MySQL
   Instance.storagePath = "3,01637037d6"
   ↓
6. Generate thumbnail (async)
   ↓
7. Upload thumbnail to SeaweedFS
   Instance.thumbnailPath = "3,01637037d7"
```

### 성능 이점

**시나리오**: 100,000개의 DICOM 파일 저장

| 지표 | 전통적 FS | SeaweedFS | 개선율 |
|-----|----------|-----------|-------|
| 디스크 Seek | 400,000회 | 100,000회 | 75% 감소 |
| 메타데이터 메모리 | 28MB | 1.6MB | 94% 감소 |
| 파일 조회 속도 | 200ms | 20ms | 10배 빠름 |
| 스토리지 오버헤드 | 28MB | 4MB | 86% 감소 |

## 다른 객체 스토리지와의 차이점

### SeaweedFS vs MinIO

| 특징 | SeaweedFS | MinIO |
|-----|-----------|-------|
| **설계 목표** | 수십억 개 작은 파일 | S3 호환성 및 성능 |
| **작은 파일 성능** | ⭐⭐⭐⭐⭐ (O(1)) | ⭐⭐⭐ |
| **S3 호환성** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **메모리 사용량** | 적음 (2-4GB) | 많음 (8GB+) |
| **Enterprise 기능** | Basic | Advanced |
| **리소스 요구사항** | Low | Medium-High |
| **복잡도** | 낮음 | 중간 |

**SeaweedFS 선택 이유** (SADO 프로젝트):
- ✅ DICOM 파일 = 작은 파일 다수 → SeaweedFS 강점
- ✅ 낮은 메모리 요구사항 → 개발 환경 친화적
- ✅ 단순한 아키텍처 → 학습 프로젝트에 적합
- ✅ O(1) 읽기 성능 → DICOM 뷰어 빠른 로딩

### SeaweedFS vs AWS S3

| 특징 | SeaweedFS | AWS S3 |
|-----|-----------|--------|
| **배포** | Self-Hosted | Cloud (Managed) |
| **비용** | 인프라 비용만 | 저장 + 요청 비용 |
| **지연시간** | 낮음 (로컬) | 높음 (네트워크) |
| **커스터마이징** | 자유로움 | 제한적 |
| **운영 부담** | 높음 | 없음 (Managed) |

**Self-Hosted 선택 이유** (SADO 프로젝트):
- ✅ 의료 데이터 → On-Premise 보안 요구사항
- ✅ 학습 목적 → 직접 운영 경험
- ✅ 비용 절감 → 학습 프로젝트 예산
