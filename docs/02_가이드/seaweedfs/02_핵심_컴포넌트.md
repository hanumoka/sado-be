## 컴포넌트 개요

### 3계층 구조

SeaweedFS는 **3개의 주요 서버 타입**으로 구성됩니다:

```
┌─────────────────────────────────────────────────┐
│         Filer Server (선택적)                   │
│    - 파일 시스템 인터페이스                      │
│    - S3 API 제공                                │
│    - 메타데이터 관리                            │
└─────────────────┬───────────────────────────────┘
                  │
┌─────────────────┴───────────────────────────────┐
│                                                  │
│  ┌─────────────────┐      ┌─────────────────┐  │
│  │ Master Server   │◄────►│ Volume Server   │  │
│  │  (필수)         │      │  (필수)         │  │
│  │                 │      │                 │  │
│  │ - 클러스터 조정 │      │ - 파일 저장     │  │
│  │ - FID 할당      │      │ - 데이터 제공   │  │
│  │ - 볼륨 관리     │      │ - 인덱스 캐싱   │  │
│  └─────────────────┘      └─────────────────┘  │
│                                                  │
│         Object Store Layer (핵심)               │
└──────────────────────────────────────────────────┘
```

### 역할 요약

| 컴포넌트 | 필수 여부 | 주요 역할 | 포트 |
|---------|----------|----------|------|
| **Master** | 필수 | 클러스터 조정, FID 할당, 볼륨 위치 관리 | 9333, 19333 |
| **Volume** | 필수 | 파일 데이터 저장, 읽기/쓰기 처리 | 8080 |
| **Filer** | 선택 | 파일 시스템 인터페이스, S3 API | 8888, 18888 |

## Master Server 상세

### 핵심 역할

Master Server는 SeaweedFS 클러스터의 **두뇌**입니다:

```
Master Server = {
    클러스터 코디네이터,
    메타데이터 관리자,
    볼륨 할당자,
    리더 선출 (Raft)
}
```

### 주요 기능

#### 1. 파일 ID (FID) 할당

클라이언트가 파일을 업로드하려면 먼저 Master에게 **FID (File ID)**를 요청합니다:

```bash
# FID 요청
curl "http://localhost:9333/dir/assign"

# 응답
{
  "fid": "3,01637037d6",
  "url": "192.168.1.100:8080",
  "publicUrl": "localhost:8080",
  "count": 1
}
```

**FID 구조**:
```
"3,01637037d6"
 │  │
 │  └─ Needle ID (파일 고유 번호)
 └──── Volume ID (어느 볼륨에 저장할지)
```

#### 2. Volume 위치 정보 관리

Master는 **어떤 Volume이 어느 Volume Server에 있는지** 추적합니다:

```go
// Master의 내부 상태 (개념)
VolumeLocationMap = {
    Volume 1: [Server A, Server B],  // 복제본 2개
    Volume 2: [Server A],
    Volume 3: [Server C, Server D],
}
```

#### 3. Heartbeat 수신

Volume Server들은 주기적으로 Master에게 **Heartbeat**를 보냅니다:

```json
// Volume Server → Master Heartbeat
{
  "ip": "192.168.1.100",
  "port": 8080,
  "volumes": [
    {
      "id": 1,
      "size": 104857600,  // 100MB
      "fileCount": 1234
    },
    {
      "id": 3,
      "size": 52428800,   // 50MB
      "fileCount": 567
    }
  ],
  "maxVolumeCount": 10
}
```

Master는 이 정보를 바탕으로:
- ✅ Volume Server 생존 여부 확인
- ✅ Volume 사용률 모니터링
- ✅ 새 Volume 할당 결정

#### 4. 복제 정책 관리

Master는 복제 정책에 따라 **어디에 복제본을 만들지** 결정합니다:

```bash
# 복제 정책 예시
weed master -defaultReplication=001

# 001 = 같은 랙에 1개 복제본
# 010 = 다른 랙에 1개 복제본
# 100 = 다른 데이터센터에 1개 복제본
```

### Master HA (High Availability)

프로덕션 환경에서는 **3개의 Master**를 Raft 합의 알고리즘으로 클러스터링합니다:

```bash
# Master 클러스터 구성 (3대)
weed master -mdir=/data/master1 -peers=ip1:9333,ip2:9333,ip3:9333
weed master -mdir=/data/master2 -peers=ip1:9333,ip2:9333,ip3:9333
weed master -mdir=/data/master3 -peers=ip1:9333,ip2:9333,ip3:9333
```

**Raft 리더 선출**:
```
┌───────────┐
│ Master 1  │ ← Leader (Active)
├───────────┤
│ Master 2  │ ← Follower (Standby)
├───────────┤
│ Master 3  │ ← Follower (Standby)
└───────────┘

Leader 장애 발생 → 자동으로 새 Leader 선출 (< 5초)
```

### Master API 엔드포인트

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/dir/assign` | GET | FID 할당 요청 |
| `/dir/lookup?volumeId=3` | GET | Volume 위치 조회 |
| `/vol/grow?count=10` | GET | Volume 추가 생성 |
| `/cluster/status` | GET | 클러스터 상태 조회 |
| `/cluster/healthz` | GET | Health Check |

### Master가 저장하지 않는 것

⚠️ **중요**: Master는 다음을 저장하지 **않습니다**:

- ❌ 파일 데이터 (Volume Server가 저장)
- ❌ 파일 메타데이터 (Filer가 저장)
- ❌ 파일 이름 (Filer가 저장)

Master는 오직 **"Volume ID가 어느 서버에 있는지"** 만 관리합니다.

## Volume Server 상세

### 핵심 역할

Volume Server는 **실제 파일 데이터를 저장하고 제공**하는 서버입니다:

```
Volume Server = {
    파일 저장소,
    Needle 관리자,
    인덱스 캐시,
    I/O 핸들러
}
```

### Volume 구조

#### Volume 파일

Volume은 물리적으로 **두 개의 파일**로 구성됩니다:

```
/data/volumes/
├── 1.dat       # 실제 파일 데이터 (최대 32GB)
└── 1.idx       # 인덱스 파일 (Needle ID → Offset)
```

**1.dat 내부 구조** (Needle 형식):

```
┌────────────────────────────────────────────────┐
│ Cookie (4 bytes) | 0x12345678                  │
│ Needle ID (8 bytes) | 0x01637037d6            │
│ Size (4 bytes) | 102400 (100KB)               │
│ Data (Size bytes) | [... file content ...]    │
│ Checksum (4 bytes) | CRC32                    │
├────────────────────────────────────────────────┤
│ Cookie (4 bytes) | 0x12345678                  │
│ Needle ID (8 bytes) | 0x01637037d7            │
│ Size (4 bytes) | 204800 (200KB)               │
│ Data (Size bytes) | [... file content ...]    │
│ Checksum (4 bytes) | CRC32                    │
└────────────────────────────────────────────────┘
```

**1.idx 내부 구조** (인덱스):

```
# 메모리에 로드되는 Index
Needle ID       → Offset      | Size
─────────────────────────────────────
0x01637037d6    → 0x00001000  | 102400
0x01637037d7    → 0x0001A000  | 204800
0x01637037d8    → 0x00052000  | 51200
```

#### O(1) 읽기 원리 (재확인)

```go
// 파일 읽기 의사 코드
func ReadFile(volumeID, needleID) {
    // 1. 메모리에서 Offset 조회 (O(1))
    offset := volumeIndex[needleID]  // 예: 0x00001000

    // 2. Volume 파일의 Offset 위치로 Seek
    file := open("/data/volumes/" + volumeID + ".dat")
    file.Seek(offset)  // 단 1번의 Disk Seek!

    // 3. 데이터 읽기
    return file.Read(size)
}
```

### Volume 크기 제한

**기본 설정**:
- **최대 크기**: 32GB (변경 가능)
- **최대 파일 수**: 약 800만 개 (32GB / 4KB 기준)

**크기 설정**:
```bash
weed master -volumeSizeLimitMB=1024  # 1GB로 제한
```

⚠️ **주의**: `volumeSizeLimitMB`는 클러스터 생성 후 변경 불가!

### Volume Server API 엔드포인트

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/{volumeId},{needleId}` | POST | 파일 업로드 |
| `/{volumeId},{needleId}` | GET | 파일 다운로드 |
| `/{volumeId},{needleId}` | DELETE | 파일 삭제 |
| `/healthz` | GET | Health Check |
| `/status` | GET | 서버 상태 조회 |

### Compaction (압축)

삭제된 파일은 실제로 삭제되지 않고 **"삭제 플래그"만** 표시됩니다. 주기적으로 **Compaction**을 실행하여 공간을 회수합니다:

```bash
# 특정 Volume Compaction
curl "http://localhost:8080/admin/volume/compact?volumeId=3"

# 결과: 삭제된 Needle 제거, Volume 크기 감소
```

## Filer Server 상세

### 핵심 역할

Filer는 **파일 시스템 인터페이스**를 제공합니다:

```
Filer Server = {
    디렉토리 관리,
    파일 메타데이터 저장,
    S3 API 제공,
    POSIX 인터페이스
}
```

### 왜 Filer가 필요한가?

**Object Store만 사용할 때의 문제**:
```bash
# FID만으로는 파일을 찾기 어려움
파일 ID: "3,01637037d6"

# 이게 무슨 파일이지? 언제 업로드했지? 누가 소유자지?
```

**Filer를 사용하면**:
```bash
# 익숙한 파일 경로로 접근
/photos/2025/12/vacation.jpg
/documents/report.pdf
/dicom/study1/series1/instance1.dcm
```

### Filer 아키텍처

```
┌─────────────────────────────────────────────┐
│              Filer Server                    │
├─────────────────────────────────────────────┤
│                                              │
│  ┌──────────────┐      ┌─────────────────┐ │
│  │   Directory  │      │  File Metadata  │ │
│  │   Structure  │      │   (Name, Size,  │ │
│  │              │      │    Owner, etc)  │ │
│  └──────┬───────┘      └────────┬────────┘ │
│         │                       │           │
│         └───────────┬───────────┘           │
│                     ↓                        │
│         ┌───────────────────────┐           │
│         │ Metadata Store        │           │
│         │ (MySQL, Postgres,     │           │
│         │  Redis, LevelDB, etc) │           │
│         └───────────────────────┘           │
│                                              │
│         ┌───────────────────────┐           │
│         │   Volume Servers      │           │
│         │  (Actual File Data)   │           │
│         └───────────────────────┘           │
└─────────────────────────────────────────────┘
```

### Filer 메타데이터 저장소

Filer는 메타데이터를 **외부 데이터베이스**에 저장합니다:

| 저장소 | 사용 시나리오 |
|-------|-------------|
| **MySQL** | 프로덕션 HA 환경 (추천) |
| **PostgreSQL** | 프로덕션 HA 환경 |
| **Redis** | 고성능 캐싱 |
| **LevelDB** | 단일 노드 개발 환경 |
| **TiKV** | 대규모 분산 환경 |

**설정 예시** (MySQL):
```toml
# filer.toml
[mysql2]
enabled = true
createTable = true
hostname = "localhost"
port = 3306
username = "root"
password = "password"
database = "seaweedfs"
connection_max_idle = 2
connection_max_open = 10
```

### S3 API 지원

Filer는 **AWS S3 호환 API**를 제공합니다:

```bash
# S3 버킷 생성
aws s3 mb s3://my-bucket --endpoint-url http://localhost:8888

# 파일 업로드
aws s3 cp file.jpg s3://my-bucket/photos/ --endpoint-url http://localhost:8888

# 파일 다운로드
aws s3 cp s3://my-bucket/photos/file.jpg . --endpoint-url http://localhost:8888
```

### Filer API 엔드포인트

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `/path/to/file` | POST | 파일 업로드 |
| `/path/to/file` | GET | 파일 다운로드 |
| `/path/to/file` | DELETE | 파일 삭제 |
| `/path/to/dir/?lastFileName=abc&limit=100` | GET | 디렉토리 목록 조회 (Pagination) |
| `/path/to/file?cp.from=/other/path` | POST | 파일 복사 |

### Filer의 장점

✅ **파일 시스템 경험**: `/photos/2025/12/vacation.jpg` 형태로 접근
✅ **메타데이터 관리**: 파일 이름, 크기, 수정 시간, 권한 등
✅ **S3 호환성**: 기존 S3 도구 및 라이브러리 사용 가능
✅ **POSIX 마운트**: FUSE를 통해 일반 디렉토리처럼 마운트 가능

## 컴포넌트 간 상호작용

### 파일 업로드 플로우 (Filer 사용)

```
┌─────────┐
│ Client  │
└────┬────┘
     │ (1) POST /photos/vacation.jpg
     ↓
┌─────────────┐
│   Filer     │
└────┬────────┘
     │ (2) Request FID
     ↓
┌─────────────┐
│   Master    │ → FID: "3,01637037d6"
└─────────────┘   URL: "192.168.1.100:8080"
     │
     ↓ (3) Upload to Volume
┌─────────────┐
│  Volume     │ → Store file data
└─────────────┘
     │
     ↓ (4) Save metadata
┌─────────────┐
│   MySQL     │ → {path: "/photos/vacation.jpg", fid: "3,01637037d6"}
└─────────────┘
```

### 파일 다운로드 플로우 (Filer 사용)

```
┌─────────┐
│ Client  │
└────┬────┘
     │ (1) GET /photos/vacation.jpg
     ↓
┌─────────────┐
│   Filer     │
└────┬────────┘
     │ (2) Query metadata
     ↓
┌─────────────┐
│   MySQL     │ → FID: "3,01637037d6"
└─────────────┘
     │
     ↓ (3) Lookup Volume location
┌─────────────┐
│   Master    │ → URL: "192.168.1.100:8080"
└─────────────┘
     │
     ↓ (4) Download file
┌─────────────┐
│  Volume     │ → Return file data
└─────────────┘
```

### 파일 업로드 플로우 (Object Store만 사용)

```
┌─────────┐
│ Client  │
└────┬────┘
     │ (1) Request FID
     ↓
┌─────────────┐
│   Master    │ → FID: "3,01637037d6"
└─────────────┘   URL: "192.168.1.100:8080"
     │
     ↓ (2) Upload directly
┌─────────────┐
│  Volume     │ → Store file data
└─────────────┘
     │
     ↓ (3) Client saves FID
┌─────────────┐
│  App DB     │ → {dicom_id: "1.2.3.4", fid: "3,01637037d6"}
└─────────────┘
```

**SADO 프로젝트 선택**: Object Store만 사용 (Filer 불필요)
- ✅ Instance 엔티티에 `storagePath = FID` 저장
- ✅ MySQL이 이미 파일 메타데이터 관리
- ✅ 단순한 아키텍처

## 단일 바이너리 아키텍처

### weed 바이너리

SeaweedFS는 **단일 Go 바이너리**로 모든 서버 타입을 실행할 수 있습니다:

```bash
# 바이너리 다운로드
wget https://github.com/seaweedfs/seaweedfs/releases/download/3.80/linux_amd64.tar.gz
tar -xzf linux_amd64.tar.gz

# 모든 서버가 같은 바이너리
./weed master    # Master Server 실행
./weed volume    # Volume Server 실행
./weed filer     # Filer Server 실행
./weed server    # All-in-One 실행 (개발용)
```

### All-in-One 서버 (개발 환경)

개발 환경에서는 **하나의 프로세스**로 모두 실행 가능:

```bash
weed server -dir=/data -volume.max=10 -s3

# 실행 결과:
# - Master: localhost:9333
# - Volume: localhost:8080
# - Filer:  localhost:8888
# - S3 API: localhost:8333
```

### 프로덕션 환경 (분리 실행)

프로덕션에서는 **각 서버를 별도 프로세스**로 실행:

```bash
# Master (3대 클러스터)
weed master -mdir=/data/master -peers=ip1:9333,ip2:9333,ip3:9333

# Volume (여러 대)
weed volume -dir=/data/volume1 -max=100 -mserver=ip1:9333,ip2:9333,ip3:9333

# Filer (여러 대)
weed filer -master=ip1:9333,ip2:9333,ip3:9333 -collection=default
```
