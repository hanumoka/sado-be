### 1.1 Race Condition in findOrCreate Pattern

**심각도**: 🔴 Critical
**영향 범위**: PatientService, StudyService, SeriesService

#### 문제 설명

`findOrCreate` 패턴에서 두 개 이상의 동시 요청이 같은 DICOM 파일을 업로드할 때, 중복 레코드가 생성될 수 있습니다.

```
Thread A: findByStudyInstanceUid("1.2.3") → Empty
Thread B: findByStudyInstanceUid("1.2.3") → Empty
Thread A: save(new Study("1.2.3"))        → ID=1
Thread B: save(new Study("1.2.3"))        → ID=2 (중복!)
```

#### 현재 코드 위치 (정확한 라인 번호)

| 파일 | 메서드 | 라인 |
|------|--------|------|
| `PatientService.java` | findOrCreatePatient | Line 88-120 |
| `StudyService.java` | findOrCreateStudy | Line 109-139 |
| `SeriesService.java` | findOrCreateSeries | Line 129-167 |

#### 해결 방안: DB Unique Constraint + DataIntegrityViolationException 처리

**전제조건**: 위의 1.0에서 Unique Constraint를 먼저 추가해야 합니다!

**PatientService.java 수정 예시**:

```java
@Transactional
public Patient findOrCreatePatient(String dicomPatientId, String issuer, ...) {
    // 1차 조회
    Optional<Patient> existing = patientRepository
        .findByDicomPatientIdAndIssuerOfPatientId(dicomPatientId, issuer);

    if (existing.isPresent()) {
        log.debug("Found existing patient: {}", existing.get().getId());
        return existing.get();
    }

    // 신규 생성 시도
    try {
        Patient newPatient = Patient.builder()
            .dicomPatientId(dicomPatientId)
            .issuerOfPatientId(issuer)
            // ... 기타 필드
            .build();
        Patient saved = patientRepository.saveAndFlush(newPatient);
        log.info("Created new patient: {}", saved.getId());
        return saved;
    } catch (DataIntegrityViolationException e) {
        // Race condition 발생 - 다른 스레드가 먼저 저장함
        log.warn("Race condition detected for patient: {}/{}", dicomPatientId, issuer);
        return patientRepository
            .findByDicomPatientIdAndIssuerOfPatientId(dicomPatientId, issuer)
            .orElseThrow(() -> new IllegalStateException(
                "Patient should exist after DataIntegrityViolationException"));
    }
}
```

**필요한 import 추가**:
```java
import org.springframework.dao.DataIntegrityViolationException;
```

#### 해결 방안 B: Pessimistic Lock 사용

더 엄격한 동시성 제어가 필요할 경우:

**PatientRepository.java 수정**:

```java
public interface PatientRepository extends JpaRepository<Patient, Long> {

    // 기존 메서드
    Optional<Patient> findByDicomPatientIdAndIssuerOfPatientId(
        String dicomPatientId, String issuerOfPatientId);

    // Pessimistic Lock 버전 추가
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Patient p WHERE p.dicomPatientId = :dicomPatientId " +
           "AND p.issuerOfPatientId = :issuer")
    Optional<Patient> findByDicomPatientIdAndIssuerWithLock(
        @Param("dicomPatientId") String dicomPatientId,
        @Param("issuer") String issuer);
}
```

**주의사항**: Pessimistic Lock은 성능 오버헤드가 있으므로, 높은 동시성이 예상되는 경우에만 사용

#### 확인 필요 사항

1. Patient Entity의 Unique Constraint 확인:
   ```java
   @Table(uniqueConstraints = {
       @UniqueConstraint(columnNames = {"tenant_id", "dicom_patient_id", "issuer_of_patient_id"})
   })
   ```

2. Study, Series Entity도 동일하게 Unique Constraint 확인

### 1.2 N+1 Query Problem

**심각도**: 🟠 Medium → 🟢 Low (재검토 결과)
**영향 범위**: Controller에서 연관 Entity 조회 시

#### 문제 설명 (재분석)

코드 검토 결과, 현재 코드에서 **실제 N+1 문제가 발생하지 않을 가능성이 높습니다**.

**PatientController.java Line 207-220** (`toStudyResponse` 메서드):
```java
private StudyResponse toStudyResponse(Study study) {
    return StudyResponse.builder()
            .id(study.getId())
            .patientId(study.getPatient().getId())  // Line 210
            // ...
}
```

**핵심 포인트**: Hibernate에서 `proxy.getId()`는 추가 쿼리 없이 ID를 반환합니다.
- Study Entity의 `patient` 필드는 `@ManyToOne(fetch = FetchType.LAZY)`
- Lazy Proxy 상태에서 `getId()`만 호출하면 FK 값을 이미 알고 있으므로 추가 쿼리 불필요
- 다만 `getPatientName()` 같은 다른 필드에 접근하면 N+1 발생

#### 현재 코드 위치 (정확한 라인 번호)

| 파일 | 메서드 | 라인 | N+1 위험 |
|------|--------|------|----------|
| `PatientController.java` | toStudyResponse | Line 207-220 | 🟢 낮음 (getId만 사용) |
| `StudyController.java` | toSeriesResponse | 확인 필요 | 미확인 |
| `SeriesController.java` | toInstanceResponse | 확인 필요 | 미확인 |

#### 권장사항: 명시적으로 안전하게 만들기

현재 문제가 없더라도, 향후 코드 변경 시 N+1이 발생할 수 있으므로 **명시적으로 안전하게** 만드는 것을 권장합니다.

**방법 A: Study Entity에 편의 메서드 추가** (권장 - 최소 변경)

`Study.java`에 추가:
```java
/**
 * Lazy loading 없이 Patient ID 반환
 * Hibernate Proxy 상태에서도 안전하게 ID만 반환
 */
public Long getPatientId() {
    return patient != null ? patient.getId() : null;
}
```

`PatientController.java` Line 210 수정:
```java
.patientId(study.getPatientId())  // 변경: getPatient().getId() → getPatientId()
```

**방법 B: @EntityGraph 사용** (완전한 해결)

`StudyRepository.java`에 추가:
```java
import org.springframework.data.jpa.repository.EntityGraph;

@EntityGraph(attributePaths = {"patient"})
List<Study> findByPatientIdOrderByStudyDateDesc(Long patientId);
```

**주의**: 이 방법은 Patient 전체를 항상 로딩하므로, 불필요한 데이터 로딩이 발생할 수 있습니다. ID만 필요한 경우 방법 A가 더 효율적입니다.

#### 결론

- **현재 상태**: 실제 N+1 발생 안 함 (getId만 사용)
- **권장 조치**: 방법 A (편의 메서드 추가)로 명시적 안전성 확보
- **우선순위**: Medium → Low로 하향 조정

### 2.1 S3 Upload-DB Save Atomicity

**심각도**: 🟠 High
**영향 범위**: InstanceController.uploadDicom()

#### 문제 설명

현재 흐름:
1. S3 업로드 성공 ✅
2. DB 저장 실패 ❌ → S3에 고아 파일 남음

```java
// 현재 코드 (문제 있음)
String s3Key = dicomStorageService.uploadDicomFile(...);  // 성공
Instance saved = instanceService.createInstance(instance);  // 실패하면?
// → s3Key에 해당하는 파일은 고아 상태
```

#### 현재 코드 위치

```
sado-minipacs/src/main/java/com/hanumoka/sado/minipacs/controller/
└── InstanceController.java (uploadDicom 메서드, 약 Line 80~120)
```

#### 해결 방안: 보상 트랜잭션 (Compensating Transaction)

**InstanceController.java 수정**:

```java
@PostMapping("/upload")
@Transactional
public ApiResponse<InstanceResponse> uploadDicom(
        @RequestParam("file") MultipartFile file) {

    String s3Key = null;

    try {
        // 1. DICOM 메타데이터 추출
        DicomMetadata metadata = dicomMetadataExtractor.extract(file.getInputStream());

        // 2. Patient/Study/Series findOrCreate
        Patient patient = patientService.findOrCreatePatient(...);
        Study study = studyService.findOrCreateStudy(...);
        Series series = seriesService.findOrCreateSeries(...);

        // 3. S3 업로드
        s3Key = dicomStorageService.uploadDicomFile(
            metadata.getStudyInstanceUid(),
            metadata.getSeriesInstanceUid(),
            metadata.getSopInstanceUid(),
            file.getInputStream(),
            file.getSize()
        );

        // 4. Instance 생성 (DB 저장)
        Instance instance = Instance.builder()
            .series(series)
            .sopInstanceUid(metadata.getSopInstanceUid())
            .storagePath(s3Key)
            .fileSize(file.getSize())
            .build();

        Instance saved = instanceService.createInstance(instance);

        return ApiResponse.success(toResponse(saved));

    } catch (Exception e) {
        // 보상 트랜잭션: S3 파일 삭제
        if (s3Key != null) {
            try {
                log.warn("Rolling back S3 upload due to error: {}", s3Key);
                dicomStorageService.deleteDicomFile(s3Key);
            } catch (Exception deleteEx) {
                log.error("Failed to delete orphan S3 file: {}", s3Key, deleteEx);
                // 고아 파일 정리 배치 작업에서 처리하도록 기록
                // orphanFileService.recordOrphanFile(s3Key);
            }
        }
        throw e;  // 원래 예외 재발생
    }
}
```

#### 추가 권장사항: 고아 파일 정리 배치

나중에 구현할 배치 작업:
1. S3의 모든 파일 목록 조회
2. DB Instance.storagePath와 비교
3. DB에 없는 파일 = 고아 파일 → 삭제 또는 보관

### 2.2 Instance 삭제 시 S3 파일 미삭제

**심각도**: 🟠 High
**영향 범위**: InstanceService.deleteInstance(), InstanceController.deleteInstance()

#### 문제 설명

Instance 삭제 시 DB 레코드만 삭제되고, S3의 실제 파일은 남아있음

```java
// 현재 코드
instanceRepository.delete(instance);  // DB만 삭제
// S3 파일은 고아 상태로 남음
```

#### 현재 코드 위치

```
sado-minipacs/src/main/java/com/hanumoka/sado/minipacs/domain/service/
└── InstanceService.java (deleteInstance 메서드)
```

#### 해결 방안

**InstanceService.java 수정**:

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class InstanceService {

    private final InstanceRepository instanceRepository;
    private final DicomStorageService dicomStorageService;  // 주입 추가
    private final FileAssetRepository fileAssetRepository;  // 주입 추가

    @Transactional
    public void deleteInstance(Long id) {
        Instance instance = instanceRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Instance not found: " + id));

        String storagePath = instance.getStoragePath();

        // 1. 연관된 FileAsset 삭제 (또는 DELETED 상태로 변경)
        List<FileAsset> fileAssets = fileAssetRepository
            .findByReferenceTypeAndReferenceId(ReferenceType.INSTANCE, id);

        for (FileAsset fileAsset : fileAssets) {
            // Soft delete
            fileAsset.markDeleted();
            // 또는 Hard delete
            // fileAssetRepository.delete(fileAsset);
        }

        // 2. DB에서 Instance 삭제
        instanceRepository.delete(instance);

        // 3. S3에서 파일 삭제
        if (storagePath != null && !storagePath.isEmpty()) {
            try {
                dicomStorageService.deleteDicomFile(storagePath);
                log.info("Deleted S3 file: {}", storagePath);
            } catch (Exception e) {
                // S3 삭제 실패 시 로그만 남기고 진행
                // 나중에 고아 파일 정리 배치에서 처리
                log.error("Failed to delete S3 file: {}. Will be cleaned up later.",
                    storagePath, e);
            }
        }
    }
}
```

**주의**: S3 삭제는 트랜잭션 외부에서 수행되므로, DB 롤백 시 S3 파일이 삭제된 상태로 남을 수 있습니다. 이는 "파일 없음"이 "고아 파일"보다 나은 상황이므로 현재 순서가 적절합니다.

#### 해결 방안

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
protected ResponseEntity<ApiResponse<?>> handleValidationException(
        MethodArgumentNotValidException ex) {

    // 필드별 에러 메시지 수집
    Map<String, String> fieldErrors = new HashMap<>();
    ex.getBindingResult().getFieldErrors().forEach(error ->
        fieldErrors.put(error.getField(), error.getDefaultMessage())
    );

    // 또는 List 형태로
    List<String> errors = ex.getBindingResult()
        .getFieldErrors()
        .stream()
        .map(e -> e.getField() + ": " + e.getDefaultMessage())
        .collect(Collectors.toList());

    log.warn("Validation failed: {}", fieldErrors);

    return ResponseEntity
        .status(CommonCode.INVALID_PARAMETER.getHttpStatus())
        .body(ApiResponse.of(CommonCode.INVALID_PARAMETER, fieldErrors));
}
```

**응답 예시**:
```json
{
  "code": 400001,
  "message": "Invalid parameter",
  "data": {
    "dicomPatientId": "must not be blank",
    "patientBirthDate": "must be a past date"
  }
}
```

### 3.3 카운터 증감 동시성 문제

**심각도**: 🟡 Medium
**영향 범위**: Study.numberOfSeries, Study.numberOfInstances, Series.numberOfInstances

#### 문제 설명

역정규화 필드 증감 시 동시 접근으로 인한 카운터 불일치 가능

```java
// Study.java
public void incrementSeriesCount() {
    this.numberOfSeries = CounterManager.increment(this.numberOfSeries);
    // 동시에 두 스레드가 호출하면 하나만 반영될 수 있음
}
```

#### 해결 방안 A: DB 레벨 락 (권장)

Service 레이어에서 Pessimistic Lock 사용:

```java
@Transactional
public Series createSeries(Series series) {
    // Study를 락과 함께 조회
    Study study = studyRepository.findByIdWithLock(series.getStudy().getId())
        .orElseThrow(() -> new ResourceNotFoundException("Study not found"));
```

### 3.4 FileAsset TTL 배치 미구현

**심각도**: 🟡 Medium
**영향 범위**: FileAsset 만료 처리

#### 현재 상태

#### 해결 방안

**FileAssetCleanupScheduler.java 신규 생성**:

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class FileAssetCleanupScheduler {

    private final FileAssetRepository fileAssetRepository;
    private final DicomStorageService storageService;  // 또는 별도 FileStorageService

    /**
     * 매시간 만료된 FileAsset 처리
     */
    @Scheduled(cron = "0 0 * * * *")
    @Transactional
    public void cleanupExpiredFiles() {
        LocalDateTime now = LocalDateTime.now();
        List<FileAsset> expiredFiles = fileAssetRepository.findExpiredFiles(now);

        log.info("Found {} expired files to clean up", expiredFiles.size());

        for (FileAsset fileAsset : expiredFiles) {
            try {
                // 1. 상태를 EXPIRED로 변경
                fileAsset.markExpired();

                // 2. S3에서 파일 삭제 (선택적)
                // storageService.deleteFile(fileAsset.getStoragePath());

                log.debug("Marked file as expired: {}", fileAsset.getId());
            } catch (Exception e) {
                log.error("Failed to process expired file: {}", fileAsset.getId(), e);
            }
        }

        fileAssetRepository.saveAll(expiredFiles);
    }

    /**
     * 매일 새벽 2시: EXPIRED 상태 파일 실제 삭제
     */
    @Scheduled(cron = "0 0 2 * * *")
    @Transactional
    public void deleteExpiredFiles() {
        // 7일 이상 EXPIRED 상태인 파일 삭제
        LocalDateTime threshold = LocalDateTime.now().minusDays(7);
        int deleted = fileAssetRepository.deleteByStatusAndUpdatedAtBefore(
            FileStatus.EXPIRED, threshold);

        log.info("Deleted {} expired files", deleted);
    }
}
```

```java
@Service
public class DicomValidationService {

    public List<ValidationLog> validate(DicomMetadata metadata,
                                        DicomMetadataRecord record) {
        List<ValidationLog> logs = new ArrayList<>();

        // Level 1: Critical (필수 태그)
        logs.add(validateLevel1(metadata, record));

        // Level 2: Warning (심초음파 표준)
        logs.add(validateLevel2(metadata, record));

        // Level 3: AI Readiness
        logs.add(validateLevel3(metadata, record));

        return validationLogRepository.saveAll(logs);
    }

    private ValidationLog validateLevel1(DicomMetadata metadata,
                                         DicomMetadataRecord record) {
        List<String> issues = new ArrayList<>();

        if (metadata.getPatientId() == null) {
            issues.add("Missing PatientID (0010,0020)");
        }
        if (metadata.getStudyInstanceUid() == null) {
            issues.add("Missing StudyInstanceUID (0020,000D)");
        }
        // ... 기타 필수 태그 검증

        return ValidationLog.builder()
            .dicomMetadataRecord(record)
            .validationLevel(DicomValidationLevel.LEVEL_1)
            .category(DicomValidationCategory.MANDATORY_TAGS)
            .status(issues.isEmpty() ?
                DicomValidationStatus.SUCCESS : DicomValidationStatus.ERROR)
            .issues(issues.isEmpty() ? null : toJson(issues))
            .validatedAt(LocalDateTime.now())
            .validatorVersion("1.0.0")
            .build();
    }
}
```
