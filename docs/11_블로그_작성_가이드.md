## 문제 정의: JPA만으로는 부족한가?

### JPA의 한계

Study 목록을 조회하는데 다음 정보가 필요하다고 가정해봅시다:
- Study 정보 (study_date, status)
- 환자 이름 (patient.name)
- Series 개수 (COUNT)

JPA로 구현하면?

**Bad (N+1 문제):**
```java
List<Study> studies = studyRepository.findAll();
for (Study study : studies) {
    String patientName = study.getPatient().getName(); // N개의 쿼리
    int seriesCount = study.getSeries().size(); // N개의 쿼리
}
```

**Better (Fetch Join):**
```java
@Query("SELECT s FROM Study s " +
       "JOIN FETCH s.patient " +
       "LEFT JOIN FETCH s.series")
List<Study> findAllWithPatientAndSeries();
```

그런데 Series 개수만 필요한데 전체 Series를 조회하는 건 비효율적입니다.

**MyBatis 해결책:**
```xml
<select id="findStudyListWithSeriesCount" resultType="StudyListDTO">
    SELECT
        s.study_id,
        s.study_date,
        s.status,
        p.patient_name,
        COUNT(sr.series_id) as series_count
    FROM study s
    INNER JOIN patient p ON s.patient_id = p.patient_id
    LEFT JOIN series sr ON s.study_id = sr.study_id
    GROUP BY s.study_id, p.patient_name
</select>
```

이 쿼리는 딱 1번만 실행되고, 필요한 데이터만 가져옵니다.

## 해결 방법: JPA + MyBatis 혼용

### 사용 기준

| 상황 | 사용 기술 | 이유 |
|------|---------|------|
| Study 생성/수정/삭제 | JPA | Dirty Checking, 도메인 모델 |
| Study 목록 조회 | MyBatis | 조인 성능, DTO 직접 매핑 |
| Study 단건 조회 | JPA | findById, Lazy Loading |
| 통계 쿼리 | MyBatis | 집계 함수, GROUP BY |

### 구현 예시

**JPA Repository (도메인 CRUD):**
```java
@Repository
public interface StudyRepository extends JpaRepository<Study, Long> {
    Optional<Study> findById(Long id);
}

@Service
public class StudyService {

    @Transactional
    public Study createStudy(StudyCreateRequest request) {
        Study study = new Study(request.getPatientId(), request.getStudyDate());
        return studyRepository.save(study); // JPA
    }
}
```

**MyBatis Mapper (조회 최적화):**
```java
@Mapper
public interface StudyQueryMapper {
    List<StudyListDTO> findStudyListWithSeriesCount();
}

@Service
public class StudyQueryService {

    private final StudyQueryMapper studyQueryMapper;

    public List<StudyListDTO> getStudyList() {
        return studyQueryMapper.findStudyListWithSeriesCount(); // MyBatis
    }
}
```

## FK 제약조건 없는 설계

### 왜 FK를 안 걸까?

**장점:**
- DB 마이그레이션 유연성 (테이블 순서 상관없이)
- 성능 (FK 체크 오버헤드 제거)
- 순환 참조 문제 회피

**단점:**
- 데이터 무결성은 애플리케이션에서 보장해야 함

### JPA에서 FK 제약 없이 관계 설정

```java
@Entity
@Table(name = "series")
public class Series {

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "study_id",
                foreignKey = @ForeignKey(ConstraintMode.NO_CONSTRAINT))
    private Study study; // 논리적 관계만
}
```

### 애플리케이션에서 무결성 보장

```java
@Transactional
public Series createSeries(Long studyId, SeriesCreateRequest request) {
    // 1. Study 존재 여부 확인 (FK 제약 대신)
    Study study = studyRepository.findById(studyId)
        .orElseThrow(() -> new StudyNotFoundException(studyId));

    // 2. Series 생성
    Series series = new Series(study, request.getSeriesNumber());
    return seriesRepository.save(series);
}
```

## 트러블슈팅

### 문제 1: MyBatis와 JPA 트랜잭션 충돌

**에러:**
```
No transactional SqlSession found
```

**원인:** MyBatis와 JPA가 서로 다른 DataSource를 사용

**해결:**
```java
@Configuration
public class MyBatisConfig {

    @Bean
    public SqlSessionFactory sqlSessionFactory(DataSource dataSource) {
        SqlSessionFactoryBean factory = new SqlSessionFactoryBean();
        factory.setDataSource(dataSource); // JPA와 동일한 DataSource
        return factory.getObject();
    }
}
```

### 문제 2: FK 없이 삭제 시 Orphan 데이터

**문제:** Study를 삭제했는데 Series가 남아있음

**해결:**
```java
@Transactional
public void deleteStudy(Long studyId) {
    // 1. 하위 데이터 확인
    if (seriesRepository.existsByStudyId(studyId)) {
        throw new StudyHasSeriesException("Cannot delete study with series");
    }

    // 2. Study 삭제
    studyRepository.deleteById(studyId);
}
```

## 핵심 정리

1. **JPA는 도메인 모델 CRUD, MyBatis는 조회 최적화**
2. **FK 제약 없이도 논리적 관계는 유지 가능**
3. **데이터 무결성은 애플리케이션 레벨에서 보장**
