## 1. 멀티모듈 구조 재검토

### 1.1 현재 제안된 구조

```
sado-be/
├── common/              # 공통 모듈
├── minipacs/            # DICOM 파일 관리
├── auth/                # 인증/인가
├── gateway/             # API Gateway
└── bff/                 # Backend For Frontend
```

### 1.2 ✅ 잘 설계된 부분

1. **명확한 책임 분리**
   - 각 모듈이 단일 책임 원칙(SRP) 준수
   - DICOM 관리, 인증, 라우팅, 비즈니스 로직이 명확히 분리
   - MSA 학습에 적합한 구조

2. **확장 가능한 아키텍처**
   - 공통 모듈을 통한 코드 재사용
   - 새로운 도메인 모듈 추가 용이
   - Gateway를 통한 단일 진입점 설계

3. **실무 패턴 적용**
   - API Gateway 패턴
   - BFF (Backend For Frontend) 패턴
   - 이벤트 기반 통신

### 1.3 ⚠️ 발견된 문제점

#### 문제 1: BFF 모듈의 과도한 책임

**현상:**
BFF 모듈이 다음 역할을 모두 담당:
- 이벤트 컨슈밍 (MiniPACS 이벤트)
- Triton 서버 연동
- 분석 결과 데이터 저장
- 리포트 생성
- 프론트엔드를 위한 API 제공

**문제:**
- BFF가 "Backend **For Frontend**"의 본래 의미를 벗어남
- 비즈니스 로직 오케스트레이션까지 담당 (단일 책임 원칙 위배)
- 테스트 및 유지보수 복잡도 증가

**영향도:** ⚠️ 중간 (아키텍처 복잡도 증가, 향후 확장성 저하)

**해결 방안:**

**Option A: 모듈 분리** (추천)
```
sado-bff/                  # Backend For Frontend
└── bff-api/              # 프론트엔드 API 조합 (GraphQL/REST 조합)

sado-orchestrator/        # 새로 추가
└── orchestrator-workflow/ # Temporal 워크플로우, 비즈니스 오케스트레이션
```

**장점:**
- 명확한 책임 분리
- BFF와 Orchestrator 패턴 모두 학습 가능
- 각 모듈의 복잡도 감소

**단점:**
- 모듈 수 증가 (5개 → 6개)
- 초기 설정 복잡도 증가

**Option B: 레이어 분리**
```
sado-bff/
├── bff-api/              # Controller, 프론트엔드 API
├── bff-workflow/         # Temporal 워크플로우
└── bff-domain/           # 도메인 로직
```

**장점:**
- 모듈 수 유지
- 내부 레이어링으로 책임 분리

**단점:**
- 여전히 하나의 서비스로 배포
- BFF의 의미가 애매해짐

#### 문제 2: MiniPACS 모듈의 범위 불명확

**현상:**
- "심장 초음파 DICOM 파일"로 한정하는지 불명확
- 프로젝트 요구사항에는 "심장 초음파"로 명시
- 하지만 MiniPACS 이름은 범용적

**문제:**
- 향후 다른 영상 타입 (CT, MRI, X-Ray 등) 추가 시 아키텍처 변경 필요
- 도메인 특화 로직 위치 불명확

**영향도:** ⚠️ 낮음 (POC 단계에서는 영향 없으나 향후 고려 필요)

**해결 방안:**

**Option A: 범용 MiniPACS + 도메인 서비스 분리**
```
sado-minipacs/            # 범용 DICOM 저장/조회
sado-echocardiography/    # 심장 초음파 특화 서비스 (향후 추가)
```

**Option B: 도메인별 서브 모듈**
```
sado-minipacs/
├── minipacs-core/        # 공통 DICOM 처리
└── minipacs-echo/        # 심장 초음파 전용
```

**추천:** POC에서는 단일 모듈로 시작, Phase 2 이후 Option A 적용

#### 문제 3: Auth 모듈의 필요성 재검토

**현상:**
- Keycloak을 사용하면 Auth 모듈이 단순 프록시 역할만 할 가능성
- Gateway에서 Keycloak을 직접 연동하는 것도 가능

**문제:**
- Auth 모듈이 추가 가치를 제공하지 못하면 불필요한 네트워크 홉
- 인프라 복잡도만 증가

**영향도:** ⚠️ 중간 (인프라 복잡도, 성능)

**해결 방안:**

**Option A: Auth 모듈 제거** (POC 단계 추천)
```
sado-gateway/
└── Keycloak 직접 연동 (Spring Security OAuth2)
```

**장점:**
- 아키텍처 단순화
- 네트워크 레이턴시 감소
- 설정 및 배포 단순화

**단점:**
- Gateway 복잡도 증가
- 인증 로직 커스터마이징 어려움

**Option B: Auth 모듈 유지 + 추가 기능 제공**
```
sado-auth/
├── 사용자 관리 (Keycloak Admin API 래핑)
├── 커스텀 인증 로직 (추가 검증, MFA 등)
└── 감사 로깅
```

**장점:**
- 관심사 분리
- 향후 확장성 (커스텀 인증 로직)
- Keycloak 의존성 격리

**단점:**
- 추가 인프라 필요
- 초기 개발 비용 증가

**추천:**
- **Phase 1 (POC)**: Option A (Gateway 직접 연동)
- **Phase 2 이후**: 필요 시 Option B로 전환

## 2. 기술 스택 타당성 재검토

### 2.1 ✅ 적절한 기술 선택

#### Kafka
- **선택 이유:** 대용량 이벤트, 순서 보장, 학습 가치
- **타당성:** ✅ 매우 적절
  - DICOM 파일 이벤트는 메타데이터가 크고, Study 단위 순서 보장 필요
  - 이벤트 소싱, CQRS 패턴 학습 가능
  - 실무에서 가장 많이 사용

#### PostgreSQL
- **선택 이유:** JSONB, 복잡한 쿼리, Temporal 백엔드 호환
- **타당성:** ✅ 매우 적절
  - DICOM 메타데이터는 복잡한 계층 구조 (JSONB로 유연하게 저장)
  - 의료 영상 리포트 생성 시 복잡한 분석 쿼리 필요
  - Temporal 백엔드로도 사용 가능 (인프라 단순화)

#### Temporal
- **선택 이유:** 분산 트랜잭션, Saga 패턴, 장기 실행 작업
- **타당성:** ✅ 적절
  - AI 분석은 장기 실행 작업 (수 분 ~ 수 시간)
  - 실패 시 자동 재시도 및 보상 트랜잭션 제공
  - 분산 트랜잭션 학습 목표와 일치

- **목적 불명확:** "POC"인지 "학습 프로젝트"인지 혼재

**영향도:** ⚠️⚠️ 높음 (프로젝트 완성도, 학습 효율성)

**해결 방안: 단계별 기술 도입**

```
Phase 1 (POC - 4주): 핵심 인프라
├─ PostgreSQL
├─ Spring Cloud Gateway
├─ Kafka (기본 Producer/Consumer)
└─ Spring Security JWT (Keycloak 대신)

Phase 2 (Learning - 2-3주): 파일 및 인증
├─ SeaweedFS (또는 로컬 파일 시스템으로 시작)
└─ Keycloak (선택적)

Phase 3 (Learning - 2-3주): 워크플로우
└─ Temporal (Saga 패턴)

Phase 4 (Advanced - 선택): 고급 기능
├─ Redis (Redisson)
├─ Debezium (선택)
└─ Monitoring Stack
```

**우선순위:** ⭐⭐⭐⭐⭐ (매우 중요)

#### 문제 6: SeaweedFS vs LocalStack S3

**현상:**
- 현재 제안: SeaweedFS (오픈소스 스토리지 학습)
- 대안: LocalStack (AWS S3 Mock)

**SeaweedFS:**
- **장점:** 오픈소스 분산 스토리지 학습, S3 호환 API
- **단점:** 상대적으로 덜 알려진 기술, AWS 실무 경험 아님

**LocalStack:**
- **장점:** 실제 AWS S3 API와 동일, 추후 AWS 전환 용이
- **단점:** SeaweedFS 자체 학습 기회 상실

**영향도:** ⚠️ 낮음 (둘 다 S3 호환 API 제공)

**해결 방안:**

**추천:**
- **AWS 실무 경험이 목표**라면 LocalStack
- **오픈소스 스토리지 학습이 목표**라면 SeaweedFS
- **POC 단계**에서는 로컬 파일 시스템 + S3 인터페이스 구현, 추후 선택

#### 문제 7: Triton 서버 Kafka 의존성

**현상:**
Triton 서버가 Kafka Consumer를 직접 구현해야 함

**문제:**
- **기술 스택 결합:** AI 팀(Python)과 백엔드 팀(Java)의 기술 스택 결합
- **Triton 복잡도:** Triton 서버는 AI 모델 서빙이 주 목적, Kafka Consumer 추가는 부담
- **의존성 추가:** Triton 서버에 Kafka 클라이언트 (Python kafka-python 등) 필요

**영향도:** ⚠️⚠️ 높음 (아키텍처 복잡도, 팀 간 결합도)

**해결 방안:**

**대안 1: REST API 기반** (POC 단계 추천)
```
BFF/Orchestrator → (HTTP POST) → Triton Server
                                      ↓
                                 비동기 처리
                                      ↓
                            (Webhook Callback or Polling)
                                      ↓
                               BFF/Orchestrator
```

**장점:**
- Triton 서버는 표준 REST API만 제공
- 기술 스택 독립성
- 구현 및 테스트 단순화

**단점:**
- Kafka의 신뢰성 및 순서 보장 이점 활용 못 함
- Polling 방식 시 레이턴시 증가

**대안 2: Message Consumer 서비스 추가** (Advanced)
```
BFF → Kafka Event B → Message Consumer Service (Java/Spring)
                              ↓
                        (HTTP POST)
                              ↓
                        Triton Server
                              ↓
                        (Callback)
                              ↓
                    Message Consumer Service
                              ↓
                        Kafka Event C
                              ↓
                            BFF
```

**장점:**
- Kafka 이벤트 기반 유지
- Triton 서버는 HTTP만 처리
- 백엔드 팀이 모든 Kafka 로직 관리

**단점:**
- 추가 서비스 필요 (복잡도 증가)

**추천:**
- **Phase 1 (POC)**: 대안 1 (REST API)
- **Phase 3 이후**: 대안 2 (메시지 변환 서비스)

#### 문제 8: 이벤트 실패 처리 전략 부재

**현상:**
아키텍처 문서에서 DLQ, 멱등성 개념은 언급했으나 구체적 전략 없음

**부족한 부분:**
1. 재시도 정책 (횟수, 간격, 백오프)
2. DLQ 모니터링 및 재처리 프로세스
3. Circuit Breaker 패턴 적용 위치

**영향도:** ⚠️ 중간 (프로덕션 준비도)

**해결 방안:**

**추천 전략:**

```markdown
## 이벤트 실패 처리 전략

### 1. 재시도 정책
- **즉시 재시도:** 3회 (네트워크 일시 장애 대응)
- **지연 재시도:** 5분, 30분, 1시간 (지수 백오프)
- **최대 재시도 후:** DLQ (Dead Letter Queue)로 이동

### 2. DLQ 모니터링
- **메트릭:** DLQ 메시지 수 (Grafana 대시보드)
- **알림:** DLQ 메시지 10개 초과 시 Slack 알림
- **재처리:** 주간 DLQ 리뷰 및 수동 재처리

### 3. Circuit Breaker
- **적용 위치:** Triton 서버 연동
- **라이브러리:** Resilience4j
- **정책:** 실패율 50% 초과 시 Circuit Open (5분)
- **Fallback:** 분석 요청을 "대기" 상태로 표시

### 4. 멱등성 보장
- **이벤트 ID:** UUID 기반 이벤트 고유 식별
- **중복 체크:** 이벤트 처리 전 DB에서 이벤트 ID 확인
- **트랜잭션:** 비즈니스 로직 + 이벤트 ID 저장 atomic 처리
```

**우선순위:** ⭐⭐⭐ (Phase 2-3에 적용)

#### 문제 9: 이벤트 버전 관리 누락

**현상:**
Schema Registry 언급했으나 구체적 버전 관리 전략 없음

**문제:**
- 이벤트 스키마 변경 시 Consumer 호환성 깨짐
- 하위 호환성 유지 어려움

**영향도:** ⚠️ 중간 (유지보수성)

**해결 방안:**

**추천: 이벤트 버전 필드 + Consumer 버전별 처리**

```java
// common-event 모듈
public abstract class BaseEvent {
    private String eventId;       // UUID
    private Instant timestamp;
    private int version;          // 스키마 버전
}

// V1 스키마
public class StudyUploadCompletedEventV1 extends BaseEvent {
    private String studyId;
    private String patientId;
    private List<String> dicomFileIds;
}

// V2 스키마 (새 필드 추가)
public class StudyUploadCompletedEventV2 extends BaseEvent {
    private String studyId;
    private String patientId;
    private List<String> dicomFileIds;
    private String studyDescription;  // 새 필드
}

// Consumer
public void handleStudyUploadEvent(BaseEvent event) {
    switch(event.getVersion()) {
        case 1:
            handleV1((StudyUploadCompletedEventV1) event);
            break;
        case 2:
            handleV2((StudyUploadCompletedEventV2) event);
            break;
        default:
            throw new UnsupportedEventVersionException(event.getVersion());
    }
}
```

**Advanced: Confluent Schema Registry + Avro**
```
- Avro로 이벤트 스키마 정의
- Schema Registry에 스키마 등록 및 버전 관리
- 자동 하위 호환성 검증
```

**추천:**
- **Phase 1-2**: 버전 필드 방식
- **Phase 3 이후**: Schema Registry (학습 목표라면)

### 4.2 ⚠️ 발견된 문제점

#### 문제 10: "POC"와 "학습 프로젝트"의 목적 충돌

**POC (Proof of Concept)의 특징:**
- 목표: 2-4주 내 핵심 기능 검증
- 범위: 최소 기능만 구현
- 결과 중심: 동작하는 프로토타입

**학습 프로젝트의 특징:**
- 목표: 깊이 있는 기술 학습
- 범위: 다양한 기술 시도
- 과정 중심: 실패와 시행착오 허용

**현재 계획의 문제:**
- "POC"라고 하면서 3-4개월 소요
- "학습"이라고 하면서 빡빡한 일정

**영향도:** ⚠️⚠️⚠️ 매우 높음 (프로젝트 방향성, 동기부여)

**해결 방안:**

**Option 1: POC 우선**
```
목표: 4주 내 핵심 플로우 동작

Week 1-2: 기반 인프라
- Gradle 멀티모듈
- PostgreSQL + Spring Boot
- Gateway 기본 라우팅

Week 3: 핵심 플로우
- DICOM 업로드 API
- Kafka 이벤트 발행
- Mock AI 분석
- 리포트 생성

Week 4: 데모
- E2E 테스트
- 데모 준비

이후: 점진적 학습
```

**Option 2: 학습 프로젝트 우선**
```
목표: 3-4개월 깊이 있는 학습

각 기술마다 충분한 시간 할애
실패와 시행착오 허용
현재 Phase 1-5 계획 유지
```

**Option 3: 하이브리드** (추천)
```

- 동작하는 E2E 플로우 (최소 기술)
- 성취감 및 동기부여

- 각 기술 하나씩 깊이 학습

- 모니터링
- 배포 자동화
```

### 5.2 Triton 서버 역할 명확화 필요

**현재 설명:**
"Triton 서버 (AI 분석 서버)"

**문제:**
- Triton 실제 의미가 불명확
- NVIDIA Triton Inference Server = AI 모델 서빙 플랫폼
- DICOM 분석 로직은 Triton이 아닌 별도 구현 필요

**명확화:**
```
Triton Server 역할:
1. AI 모델 로딩 (심장 초음파 분석 모델)
2. 추론 요청 처리 (DICOM → 분석 결과)
3. 배치 처리 지원

구현:
- sado-ai 프로젝트에 Triton Server 설정
- Python 전처리/후처리 로직
- REST API로 추론 요청 수신
```

**영향도:** ⚠️ 낮음 (명확화만 필요)

---

### 5.3 DICOM 파일 처리 복잡도

**현재 문서:**
"dcm4che 라이브러리 활용"

**추가 고려사항:**
- DICOM 파일 파싱 및 검증
- 메타데이터 추출 (Patient, Study, Series, Instance 계층)
- 이미지 데이터 추출 및 썸네일 생성
- DICOM 표준 준수 검증

**제안:**
- **Phase 1**: 간단한 DICOM 파일만 (Single Frame)
- **Phase 2**: Multi-frame, Compressed DICOM 지원 확장

**영향도:** ⚠️ 중간 (구현 복잡도)

---

### 5.4 보안 고려사항 추가 필요

**현재 문서:** PHI 보호, HTTPS/TLS, 접근 제어, 감사 로그

**추가 권장사항:**

```
1. DICOM 파일 익명화 (De-identification)
   - Patient Name, ID 등 PHI 제거 또는 해시 처리
   - 개발/테스트 환경에서 실제 환자 데이터 사용 금지

2. GDPR/HIPAA 준수 (학습 목적이더라도 인식)
   - 데이터 보관 기간 정책
   - 데이터 삭제 요청 처리 (Right to be Forgotten)

3. Rate Limiting (DDoS 방어)
   - API Gateway 레벨 적용
   - IP 기반 또는 사용자 기반

4. 입력 검증
   - DICOM 파일 크기 제한 (예: 100MB)
   - 파일 포맷 검증 (DICOM magic number 확인)
   - 악성 파일 업로드 방지
```

**영향도:** ⚠️⚠️ 높음 (보안 컴플라이언스)

**우선순위:** ⭐⭐⭐⭐ (Phase 1부터 적용)
