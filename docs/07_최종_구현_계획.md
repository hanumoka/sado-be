## 🏗️ 최종 아키텍처

### SADO 프로젝트 전체 구조

```
sado/
├── sado_be/    # Spring 멀티모듈 백엔드 + 통합 문서관리
├── sado_fe/    # React 프론트엔드
└── sado_ai/    # Triton AI 분석 서버 (심장 초음파) ⭐
```

### 멀티모듈 구조 (6개 모듈)

```
sado-be/
│
├── sado-common/                    # 1. 공통 모듈
│   ├── common-core/               # 공통 유틸, DTO, Exception
│   ├── common-event/              # 이벤트 스키마 (버전 관리)
│   └── common-security/           # 공통 보안 설정
│
├── sado-infrastructure/           # 2. 인프라 모듈
│   ├── kafka-config/             # Kafka 설정 및 Producer/Consumer
│   ├── redis-config/             # RedissonClient 설정
│   ├── temporal-config/          # Temporal Worker 설정
│   └── storage-config/           # SeaweedFS/S3 클라이언트
│
├── sado-gateway/                  # 3. API Gateway
│   ├── filters/                  # Custom Filters
│   └── config/                   # Gateway 설정
│
├── sado-minipacs/                 # 4. DICOM 파일 관리 서비스
│   ├── minipacs-api/            # REST API Layer
│   ├── minipacs-domain/         # Domain Layer
│   └── minipacs-storage/        # SeaweedFS 연동
│
├── sado-orchestrator/             # 5. 비즈니스 워크플로우 오케스트레이션 ⭐
│   ├── orchestrator-workflow/   # Temporal Workflow (Saga)
│   └── orchestrator-api/        # 내부 API (선택)
│
└── sado-bff/                      # 6. Backend For Frontend ⭐
    └── bff-api/                  # 프론트엔드 API 조합
```

### 모듈별 책임

| 모듈 | 주요 책임 | 핵심 기술 |
|------|-----------|----------|
| **Gateway** | API 진입점, 라우팅, 인증 | Spring Cloud Gateway, JWT/Keycloak |
| **MiniPACS** | DICOM 파일 업로드/저장/조회 | SeaweedFS, dcm4che, Kafka Producer |
| **Orchestrator** | 비즈니스 워크플로우, AI 연동 | Temporal Saga, Kafka Consumer, **gRPC (sado_ai)** |
| **BFF** | 프론트엔드 API 조합 | Feign Client, Redis 캐싱 |
| **Infrastructure** | 인프라 설정 추상화 | Kafka, Redis, Temporal, Storage |
| **Common** | 공통 기능 | Utils, Events, Security |

### Orchestrator 분리 이유

**기존 문제 (BFF가 모든 것을 처리):**
- 이벤트 컨슈밍 + AI 연동 + 리포트 생성 + 프론트엔드 API
- 단일 책임 원칙(SRP) 위배
- 테스트 및 유지보수 복잡도 증가

**분리 후 (명확한 책임):**
- **Orchestrator**: 비즈니스 워크플로우만 (Temporal Saga)
- **BFF**: 프론트엔드 API 조합만
- 각 모듈의 복잡도 감소, 독립적 확장 가능

## 🔄 Master-Slave Replication 운영 전략

### 개발 단계별 DB 구성

**Week 2-13: 단일 MySQL (Master 역할)**
- 개발 환경에서는 Master DB만 사용
- application.yml에 Master 연결 설정

**Week 14: Master-Slave 구성 테스트 (선택)**
- Docker Compose로 MySQL Master-Slave 구성
- Spring Boot에서 Master/Slave 라우팅 설정

### 설정 예시

```yaml
# application.yml
spring:
  datasource:
    master:
      driver-class-name: com.mysql.cj.jdbc.Driver
      jdbc-url: jdbc:mysql://localhost:3306/sado_master
      username: sado
      password: sado123
    slave:
      driver-class-name: com.mysql.cj.jdbc.Driver
      jdbc-url: jdbc:mysql://localhost:3307/sado_slave
      username: sado_read
      password: sado123
```

### 라우팅 전략

- JPA @Transactional(readOnly = true) → Slave
- JPA @Transactional → Master
- MyBatis 조회 → Slave
- MyBatis 수정 → Master

### 구현 예시

```java
@Configuration
public class DataSourceConfig {
    @Bean
    public DataSource routingDataSource() {
        RoutingDataSource routingDataSource = new RoutingDataSource();

        Map<Object, Object> dataSourceMap = new HashMap<>();
        dataSourceMap.put("master", masterDataSource());
        dataSourceMap.put("slave", slaveDataSource());

        routingDataSource.setTargetDataSources(dataSourceMap);
        routingDataSource.setDefaultTargetDataSource(masterDataSource());

        return routingDataSource;
    }
}
```

### 주의사항

- **Replication Lag 처리**: Slave에서 읽은 데이터가 최신이 아닐 수 있음
- **트랜잭션 경계**: 쓰기 후 즉시 읽기가 필요한 경우 Master 사용
