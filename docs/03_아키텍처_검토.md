## 2. 기술 스택 타당성 검토

### 2.1 메시지 브로커: Kafka vs RabbitMQ

| 항목 | Kafka | RabbitMQ |
|------|-------|----------|
| **처리량** | 매우 높음 (100k+ msg/sec) | 보통 (10-20k msg/sec) |
| **메시지 순서 보장** | 파티션 레벨에서 보장 | Queue 레벨에서 보장 |
| **메시지 보관** | 장기 보관 가능 (로그 기반) | 소비 후 삭제 |
| **복잡도** | 높음 | 중간 |
| **학습 목적 적합성** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| **의료 영상 적합성** | ⭐⭐⭐⭐⭐ (대용량 이벤트) | ⭐⭐⭐ |

#### **추천: Kafka**

**이유:**
- DICOM 파일은 대용량이며, Study 단위 이벤트 처리 시 순서 보장 필요
- 이벤트 소싱, CQRS 패턴 학습에 유리
- Debezium과의 연동성 우수
- 실무에서 더 많이 사용되는 추세

**대안:**
- 초기 POC에서는 RabbitMQ로 시작 후, Kafka로 마이그레이션하는 학습 경로도 가능

### 2.2 데이터베이스: PostgreSQL vs MySQL

| 항목 | PostgreSQL | MySQL |
|------|------------|-------|
| **JSON 지원** | 우수 (JSONB) | 보통 |
| **복잡한 쿼리** | 우수 (Window Function, CTE) | 보통 |
| **확장성** | 우수 (Extension) | 보통 |
| **DICOM 메타데이터 저장** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| **학습 곡선** | 중간 | 낮음 |
| **커뮤니티** | 활발 | 매우 활발 |

#### **추천: PostgreSQL**

**이유:**
- DICOM 메타데이터는 복잡한 계층 구조 (JSONB로 저장 가능)
- 의료 영상 리포트 생성 시 복잡한 분석 쿼리 필요
- PostGIS 확장으로 공간 데이터 처리 가능 (향후 3D 이미지 처리 시)
- Temporal과의 호환성 우수

### 2.3 Temporal vs Spring Batch

| 항목 | Temporal | Spring Batch |
|------|----------|--------------|
| **분산 워크플로우** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| **재시도 및 보상** | 자동 | 수동 구현 필요 |
| **장기 실행 워크플로우** | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| **학습 곡선** | 높음 | 중간 |
| **DICOM 분석 워크플로우** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |

#### **추천: Temporal (학습 목적에 부합)**

**이유:**
- AI 분석은 장기 실행 작업 (수 분 ~ 수 시간)
- 실패 시 자동 재시도 및 보상 트랜잭션
- 분산 트랜잭션 학습 목표와 일치
- 최신 기술 스택 (이력서 경쟁력 향상)

**주의사항:**
- 인프라 복잡도 증가 (Temporal Server, DB 필요)
- 초기 학습 비용이 높음

### 2.4 Debezium 필요성 검토

#### **Debezium 사용 사례**
- DB 변경 사항을 Kafka 이벤트로 발행 (CDC)
- 레거시 시스템 통합
- 이벤트 소싱 패턴 구현

#### **현재 프로젝트 적용 검토**

| 시나리오 | Debezium 필요 여부 | 대안 |
|----------|-------------------|------|
| MiniPACS에서 Study 업로드 완료 이벤트 발행 | ❌ 불필요 | 애플리케이션 레벨 이벤트 발행 |
| BFF에서 분석 결과 저장 시 이벤트 발행 | ❌ 불필요 | 애플리케이션 레벨 이벤트 발행 |
| 외부 레거시 시스템과 통합 | ✅ 필요 | - |
| 감사 로그 및 이벤트 소싱 | △ 선택적 | Outbox Pattern |

#### **결론: Phase 1-3에서는 불필요**

**이유:**
- 애플리케이션 코드에서 명시적으로 이벤트 발행 가능
- Debezium은 추가 인프라 복잡도 증가
- 학습 목적으로는 Phase 4에서 추가 고려

**대안:**
- **Outbox Pattern**: 트랜잭션과 이벤트 발행을 원자적으로 처리
  ```
  DB 트랜잭션:
    1. 비즈니스 데이터 저장
    2. Outbox 테이블에 이벤트 저장

  별도 프로세스:
    3. Outbox 테이블 폴링
    4. Kafka에 이벤트 발행
    5. Outbox 레코드 삭제
  ```

## 3. 아키텍처 설계 검토

### 3.1 이벤트 기반 아키텍처 (EDA) 분석

#### **제안된 이벤트 플로우**
```
DICOM Upload → Event A (Study Upload Completed)
             ↓
         BFF (Consumer)
             ↓
         Event B (Study Analysis Request)
             ↓
      Triton Server (AI)
             ↓
         Event C (Analysis Completed)
             ↓
         BFF (Consumer)
             ↓
      Report Generation
```

#### **이벤트 설계 검토**

##### ✅ **장점**
- 서비스 간 느슨한 결합
- 비동기 처리로 성능 향상
- 확장성 및 유연성

##### ⚠️ **개선 제안**

1. **이벤트 스키마 정의**
   ```java

       private List<String> dicomFileIds; // SeaweedFS File IDs
       private Instant timestamp;
       private int version;               // 스키마 버전
   ```

2. **이벤트 버전 관리**

   - Avro 또는 Protobuf로 스키마 정의

3. **실패 처리 (Dead Letter Queue)**

### 3.2 Saga 패턴 적용 (분산 트랜잭션)

#### **시나리오: DICOM 업로드 및 분석 워크플로우**

```
┌─────────────────────────────────────────────────────┐
│         Temporal Saga Workflow                      │
├─────────────────────────────────────────────────────┤
│                                                     │
│  1. UploadDicomActivity                            │
│     └─> Success: SeaweedFS에 파일 저장              │
│     └─> Failure: Compensate (파일 삭제)            │
│                                                     │
│  2. CreateStudyActivity                             │
│     └─> Success: DB에 Study 레코드 생성             │
│     └─> Failure: Compensate (Study 삭제, 파일 삭제) │
│                                                     │
│  3. RequestAnalysisActivity                         │
│     └─> Success: Triton에 분석 요청                 │
│     └─> Failure: Compensate (Study 상태 업데이트)   │
│                                                     │
│  4. WaitForAnalysisActivity                         │
│     └─> Timeout: 30분                              │
│     └─> Failure: Compensate (분석 취소 요청)        │
│                                                     │
│  5. SaveAnalysisResultActivity                      │
│     └─> Success: 분석 결과 저장                     │
│     └─> Failure: Compensate (재시도)               │
│                                                     │
│  6. GenerateReportActivity                          │
│     └─> Success: 리포트 생성                        │
│     └─> Failure: Compensate (수동 리포트 생성 대기) │
│                                                     │
└─────────────────────────────────────────────────────┘
```

#### **코드 예시**
```java
@WorkflowInterface
public interface DicomAnalysisWorkflow {
    @WorkflowMethod
    AnalysisResult processDicomStudy(StudyRequest request);
}

@WorkflowImpl(taskQueues = "dicom-analysis")
public class DicomAnalysisWorkflowImpl implements DicomAnalysisWorkflow {

    private final DicomActivities activities =
        Workflow.newActivityStub(DicomActivities.class);

    @Override
    public AnalysisResult processDicomStudy(StudyRequest request) {
        Saga saga = new Saga(new Saga.Options.Builder()
            .setParallelCompensation(false)
            .build());

        try {
            // 1. DICOM 파일 업로드
            FileUploadResult uploadResult = saga.addCompensation(
                () -> activities.deleteDicomFiles(uploadResult.getFileIds()),
                () -> activities.uploadDicomFiles(request)
            );

            // 2. Study 생성
            Study study = saga.addCompensation(
                () -> activities.deleteStudy(study.getId()),
                () -> activities.createStudy(uploadResult)
            );

            // 3. AI 분석 요청
            AnalysisJob job = saga.addCompensation(
                () -> activities.cancelAnalysis(job.getId()),
                () -> activities.requestAnalysis(study)
            );

            // 4. 분석 결과 대기 (최대 30분)
            AnalysisResult result = Workflow.await(
                Duration.ofMinutes(30),
                () -> activities.checkAnalysisStatus(job.getId())
            );

            // 5. 결과 저장 및 리포트 생성
            activities.saveAnalysisResult(result);
            Report report = activities.generateReport(result);

            return new AnalysisResult(study, result, report);

        } catch (Exception e) {
            saga.compensate(); // 모든 보상 트랜잭션 실행
            throw e;
        }
    }
}
```

#### **인증 필터 구현**
```java
@Component
public class AuthenticationFilter implements GatewayFilter {

    @Autowired
    private JwtUtil jwtUtil;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();

        if (!request.getHeaders().containsKey(HttpHeaders.AUTHORIZATION)) {
            return onError(exchange, "No Authorization header", HttpStatus.UNAUTHORIZED);
        }

        String token = request.getHeaders()
            .getFirst(HttpHeaders.AUTHORIZATION)
            .replace("Bearer ", "");

        try {
            jwtUtil.validateToken(token);
        } catch (JwtException e) {
            return onError(exchange, "Invalid token", HttpStatus.UNAUTHORIZED);
        }

        return chain.filter(exchange);
    }
}
```

```java
public class DicomController {
```
